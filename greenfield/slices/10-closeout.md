## 1. fs receipt(D-06,SL-06 的另一半)

第三种证据体制 `receipts: "fs"`。

- **是什么**:claims 内每条路径的 digest 集合——正是 `artifactCheckpoint` 已经在
  算的那个东西。`commit_oid`、`parent_oid`、`head_before` 一律 null。
- **clean 的判据**:运行时把它 claim 的东西**全都读到了**。有读不到的条目
  (权限、特殊文件)→ `uncertain`,理由逐条列出。与 git 侧同一条原则:
  **不能归因的空,永远不是 clean。**
- **是否在场**:重新算一遍,digest 集合仍然相同 → 在场;变了 → `drifted`。
  这是 git 侧"祖先 + 四种漂移"在没有版本历史时的等价物:**没有历史可依,就只能
  比对现在与当时**。
- **不做 `unlanded`**:fs 没有"落地"这回事。一份文件 digest 集要么还对得上,
  要么对不上。

### 1.1 为什么不是"给 none 加上证据"

`none` 的含义是**这个循环只凭判据认证**,那是一个合法且常见的选择(判据自己就
读文件,再记一份 digest 并不增加什么)。`fs` 是另一个选择:**我要一份可复核的
制品快照绑进认证**。两者的差别是认证标准,而认证标准必须显式(切片 2 §5)。

## 2. 判据孤儿(D-03)

运行时正常退出时会杀掉判据进程组;**自身被 SIGKILL 时无人接管**,那个进程组
留在系统里。

- **机制**:spawn 之后立刻把 pid 写进 store 的 `locks/criterion-<loop>.pid`,
  settle 时删掉。
- **收割**:下一次 `observe` 开始时,若该文件存在:pid 已死 → 只删文件;pid
  还活着 → 那是上一个被强杀的运行时留下的,**杀掉它的进程组**并把这件事写进
  本轮的 summary。
- **为什么写进 summary 而不是新记录**:它是一次执行的现场事实,和"判据的孙进程
  可能存活"同类,而 summary 是这两者已经在用的通道。**新增一种记录要有它自己的
  读者**,这里没有。

**仍然做不到的**:运行时被强杀、而**此后再没有人碰这个循环**,那个进程组就没有
人收割。这与 D-01 的形状相同——**能被发现、能被收拾,但要有人再来一次**。

## 3. 安装器(D-05):裁决为不做

挂账时的理由是"绿地还没定义发行形态"。现在看清楚了:**发行形态早就有了,而它
不需要安装器。**

- 运行时是一个**零依赖的 Node 包**,`package.json` 里一个 `bin`。分发方式就是
  npm/tarball,安装由 npm 完成——**幂等与版本化激活都是它的事,不是我们的**。
- HF-06 改写后剩下的不变式是"**宿主的任何配置字节不变**"。**没有安装器,这条
  由构造成立**:没有代码去读或写宿主配置。
- 随之了结的 WN-06(安装锁收割):**没有安装锁**。

**仍要验的是 WN-01 的实质**:装好之后,那个 bin 在三种平台上真的能被调用。这不
需要安装器,需要一次**打包并安装的验证**——CI 里 `npm pack` + 安装 + 跑
`workloop --help`。发行物能不能用,只有装一次才知道。

**Flip 条件**:出现必须落在宿主机器上、且 npm 装不了的资产。

### 3.1 打包一跑就发现的事〔实现期〕

第一次真的 `npm pack`,发行物是 **247 个文件 788K**,其中 139 个是**上一版实现的
文档**,33 个是旧世界的议题。HF-08 明写"发行物只含现行运行时",而当时那条测试
检的是**源码里有没有退役的字符串**——它一条都没漏,发行物却装着整座旧世界。

裁决:`package.json` 加 `files`,发行物只含 `src`、`bin`、`greenfield/WORKFLOW.md`
(HF-09 说的"随发行的工作流文本")。**HF-08 的测试改为问 `npm pack` 本身**:
读源码说不出发行物里有什么。现在是 **23 个文件 60K**。

## 4. WT-09(D-07):维持不做,并复核前提

前提是"没有任何动词会选择一个 worktree"。复核:公开动词表里没有任何一个接受
worktree 或分支,`--root` 是工作区路径而非 worktree 选择器。前提仍然成立,
维持不做,flip 条件不变。
