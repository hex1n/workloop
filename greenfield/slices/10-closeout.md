## 1. fs receipt(D-06,SL-06 的另一半)

第三种证据体制 `receipts: "fs"`。

- **是什么**:claims 内每条路径的 digest 集合——正是 `artifactCheckpoint` 已经在
  算的那个东西。`commit_oid`、`parent_oid`、`head_before` 一律 null。
- **clean 的判据**:运行时把它 claim 的东西**全都读到了**。有读不到的条目
  (权限、特殊文件)→ `uncertain`,理由逐条列出。与 git 侧同一条原则:
  **不能归因的空,永远不是 clean。**
- **是否在场**:重新算一遍,digest 集合仍然相同 → 在场;变了 → `drifted`。
  这是 git 侧"祖先 + 四种漂移"在没有版本历史时的等价物:**没有历史可依,就只能
  比对现在与当时**。
- **不做 `unlanded`**:fs 没有"落地"这回事。一份文件 digest 集要么还对得上,
  要么对不上。

### 1.1 为什么不是"给 none 加上证据"

`none` 的含义是**这个循环只凭判据认证**,那是一个合法且常见的选择(判据自己就
读文件,再记一份 digest 并不增加什么)。`fs` 是另一个选择:**我要一份可复核的
制品快照绑进认证**。两者的差别是认证标准,而认证标准必须显式(切片 2 §5)。

## 2. 判据孤儿(D-03)

运行时正常退出时会杀掉判据进程组;**自身被 SIGKILL 时无人接管**,那个进程组
留在系统里。

- **机制**:spawn 之后立刻把 pid 写进 store 的 `locks/criterion-<loop+command>.pid`,
  settle 时删掉。**每次尝试一份记号**〔评审后修订〕——判据在 store 锁外运行,同一个
  循环的两次观测共用一个文件名时,先结束的那次会删掉另一次仍然活着的记录。
- **发现,不收割**〔评审后修订〕:下一次 `observe` 开始时,若该文件存在:pid 已死
  → 只删文件;pid 还活着 → **把它指名写进本轮 summary,不杀**。

  初版是杀。评审指出:`process.kill(pid, 0)` 只证明**某个**进程占着那个号,而 pid
  会被回收——而 `killTree` 杀的是整个**进程组**。**凭一个数字对可能属于别人的进程组
  发 SIGKILL**,正是这个运行时在别处一概拒绝的那种不可逆猜测。

  于是与 D-01 划同一条线:**能被指名是本分,替人做不可逆的决定不是。**
- **为什么写进 summary 而不是新记录**:它是一次执行的现场事实,和"判据的孙进程
  可能存活"同类,而 summary 是这两者已经在用的通道。**新增一种记录要有它自己的
  读者**,这里没有。

**仍然做不到的**:运行时被强杀、而**此后再没有人碰这个循环**,那个进程就没人指出来。
与 D-01 同形——**能被发现,但要有人再来一次**。

## 3. 安装器(D-05):裁决为不做

挂账时的理由是"绿地还没定义发行形态"。现在看清楚了:**发行形态早就有了,而它
不需要安装器。**

- 运行时是一个**零依赖的 Node 包**,`package.json` 里一个 `bin`。分发方式就是
  npm/tarball,安装由 npm 完成——**幂等与版本化激活都是它的事,不是我们的**。
- HF-06 改写后剩下的不变式是"**宿主的任何配置字节不变**"。**没有安装器,这条
  由构造成立**:没有代码去读或写宿主配置。
- 随之了结的 WN-06(安装锁收割):**没有安装锁**。

### 3.2 HF-06 四条断言各自的下场〔评审后写清〕

初版把 HF-06 整条指向 CI,**说过头了**。逐条:

| 断言 | 下场 |
| --- | --- |
| 重复安装幂等 | **npm 的事**;门禁里连装两次并比对文件清单(§3.4) |
| 升级切换 release 原子:**激活清单指向唯一现行版本** | **作废**:没有 release 清单,没有激活步骤 |
| 升级切换 release 原子:**旧版本清理**〔第二轮评审后拆出〕 | **做了**:门禁里种一个现行发行物不含的文件再装一次,它必须消失(§3.5) |
| 宿主配置字节不变 | **由构造成立**:没有代码读或写它 |
| 安装锁可收割已死持有者 | **作废**:没有安装锁(WN-06 随之) |

初版把"升级切换 release 原子"整条判了作废,理由是"没有 release 清单,没有激活
步骤"。**那个理由只够判它的前半句。**"旧版本清理"不依赖任何清单——它问的是
装新版会不会把旧版的文件留在里面,而这件事在 npm 装包时**每次都在发生**,可测。
**一个作废的理由不能顺手带走它盖不住的那半句。**

所以 HF-06 与 WN-06 在覆盖表里仍指向**本文这条裁决**,但裁决本身现在逐句成立,
而不是整条指向一条 CI 步骤——**一条 CI 步骤担不起四条断言**。

### 3.3 WN-01 要的是三种壳,不是三个平台〔评审后修订〕

初版的 CI 步骤只有一步、没有 `shell:` 键,于是 Windows 上只跑了 GitHub 的默认壳
(pwsh),`cmd` 与 Windows PowerShell 从未被调用;而那一步用的是 POSIX 语法,
在 pwsh 下根本不成立——**并且它一次都没跑过**,分支上没有 CI 记录。我在规格里把
"三种壳"写成了"三个平台",**那是把断言改小了**。

**Flip 条件**:出现必须落在宿主机器上、且 npm 装不了的资产。

### 3.4 断言从 CI 挪进门禁〔第二轮评审后〕

上一版把三种壳写成了三条 YAML 步骤。写对了断言,**放错了地方**:

- 它**只有 CI 能跑**,而这个分支还没有 CI 记录。一条从没执行过的断言,和一条
  没被证明能变红的测试是同一样东西——**本项目对后者的标准就是它的标准**。
- 它**无法被变异探测**。规格里每条机制都要"还原后有测试变红";住在 YAML 里的
  断言没有这个环节可走。
- 它把**壳的方言**和**要证明的性质**焊死了。要证的是"打包物装得进一个含空格与
  CJK 的前缀、装两次仍然一样、装完能被调用";壳只是调用它的人。

现在 `tests/release.test.mjs` 做这件事,`node --test` 到哪它就到哪:pack → 用
**空缓存 + `--offline`** 装两次(零依赖的包无处可取,门禁不该依赖网络)→ 比对
两次安装后的文件清单(HF-06 唯一活着的那条断言)→ 对每种壳写一份**不含任何
非 ASCII 的**脚本,把那个别扭的路径**用环境变量递进去**(环境变量由系统按
Unicode 传递,写进批处理文件的字面量则要看壳猜哪个代码页)。

两处顺带修掉的:

- `spawnSync("npm", …)` **在 Windows 上根本起不来**——那里 PATH 上的是 `npm.cmd`,
  而 Node 补掉参数注入洞之后拒绝无 shell 执行 `.cmd`。HF-08 的打包检查从写下就
  是坏的,只是没有平台跑到它。改为用本进程的 `node` 执行 npm 自己的入口:不过
  shell,就没有引号规则,也没有代码页。
- 覆盖表的开场白写着"三种去处,没有第四种",而门禁只检查**路径存在**——于是
  WN-01 指着一份 YAML 走了一个切片。门禁现在检查去处的**形状**。

CI 那一步随之只剩 `npm test` 一条。它仍然是让 Windows 那半边真的被执行的唯一途径,
但它不再是那半边**唯一的住处**。

### 3.6 CI 第一次真的跑了〔推分支之后〕

WN-01 的三种壳**在 Windows 上全过**(`ok 151`)。挂了两轮的"未测"清掉了。

同一次运行里,**18 条别的测试红了**——macOS 全绿,Ubuntu 1 条,Windows 17 条。
于是有一句我写了很多遍的话被推翻:"全量 222/222 绿"从来只是**darwin 上的
222/222**。三个平台里我验过一个,却把它写成了全量。

一条是真的运行时缺陷,其余七条是测试把平台形状写死了:

| | 性质 |
| --- | --- |
| 释放锁的 rename 撞上读 `owner.json` 的等待者 → EPERM | **运行时**。见下 |
| 投影形状门禁哈希文件字节,而 Windows 检出是 CRLF | 门禁**自己**平台脆 |
| "大小写敏感就跳过"的守卫从不触发 | **假守卫**,Linux 上跑的是另一个场景 |
| 测试夹具用 `realpathSync`,运行时用 `.native` | 8.3 短名两种拼写(23 处) |
| CC-03 期望 `path.join`,而身份存规范 `/` | 期望过期 |
| 崩溃矩阵断言 `signal === "SIGKILL"` | Windows 没有信号(9 条) |
| 先删目录再 `chdir` 回来 | 钩子注册顺序,Windows 拒删 cwd |
| `process.kill(-pid)` | Windows 没有进程组 |

**运行时那条**:锁是一个目录,释放靠 rename 作证;Windows 不允许 rename 一个还有
句柄开着的目录,而每个等待者每 20ms 就读一次 `owner.json`。**释放的证明,和等待
它的人的轮询,撞在一起了**——按 LK-04 这会毒化整个进程,所以一次不巧的窥视就能
带走全部。裁决:重试(mkdir 仍然说这个进程持有锁,重试证明不是猜),**且只在
win32 重试**——同样的错误码在 POSIX 上是永久的(不可写的父目录永远 EACCES),
把它们当成到处都是"竞争"就是把"你不许"读成半秒钟的指望。

**崩溃矩阵那条值得单说**。直译成 `status === 1` 会比原缺陷更糟:Node 的语法错误
也退出 1,于是断言会继续通过而什么都不再证明——**而它存在的全部理由就是挡住这个**。
改为子进程在被杀之前**同步写下它到达了哪个相位**:这是信号一直以来的替身,而且
在两个平台上都比信号更强(SIGKILL 原则上可能来自别处)。

**第二次运行:三平台 × 两个 Node 版本全绿**,每格 224 条 0 失败。两条 skip 各自
点名——Windows 跳过"释放失败保留现场"(那条用 POSIX 权限语义构造),Ubuntu 跳过
大小写那条并写明为什么。**一条被点名的跳过是账,一条静默的 `return` 不是**,这也
正是本轮把那个假守卫改掉的理由。

### 3.7 打包清单看不见的残留〔CI 首次运行时发现〕

推分支时跟着跑起来的还有 `multi-root-authority-spike.yml`——**上一版实现的 CI**,
`on: push` 无过滤,26 秒就红了:它要跑的 `spikes/` 与 `tests/multi-root-authority-*`
在绿地上根本不存在。

这和 §3.1 是**同一类残留**,但躲过了同一道门禁:HF-08 现在问的是 `npm pack` 的
清单,而 `.github/` 不在发行物里——**发行物的边界不是仓库的边界**。裁决:删掉。
绿地是零继承重建,旧世界的 CI 不在这条分支上有位置。

### 3.5 WN-01 三条断言各自的下场〔第二轮评审后〕

§3.3 抓到"我把三种壳写成了三个平台",然后**只修了那一句**,没有把整条断言逐句
过一遍——于是同一个形状在**另外两句上**原样留着。逐句:

| 断言 | 下场 |
| --- | --- |
| 含空格与 CJK 的路径下安装两次幂等 | **做了**:前缀是 `前缀 with space`,装两次后比对文件清单 |
| 升级后**激活清单换代** | **作废**:没有 release 清单,没有激活步骤(与 HF-06 同一条裁决) |
| 升级后**运行时目录只剩现行版本** | **做了**:见下 |
| 三种 shell 各自能调用 CLI | **做了**:Windows 三份脚本,POSIX 一份 |
| 并得到**正确契约版本** | **做了,但换了度量**:见下 |

**"运行时目录只剩现行版本"怎么测**:装完之后,往安装出来的包目录里种一个
**现行发行物并不包含**的文件——那正是"上一版有、这一版删掉了的源文件"在磁盘上
的样子——再装一次,它必须消失。装同一个版本两次永远抓不到这件事:两次的内容
一模一样,合并与替换看起来没有区别。

**"正确契约版本"怎么测**:这个运行时**不报版本号**,也没有 `--version`——公开
动词表里没有它,而为了让一条断言好测就给运行时加一个面,是**让测试反过来决定
产品形态**。它的契约面是**动词表**:`--help` 打出的那张表与本源码树的 `VERBS`
必须逐项相同。这同时挡住了另一件事——机器上恰好装着另一个 workloop 时,壳可能
根本没走到刚装的这一个;一句 banner 谁都打得出,一张对得上的动词表不行。

**没有换成更弱的东西,但换了**:这里比对的是契约面而不是版本字符串。写下来,
因为§3.3 那次的教训正是"断言被改小了而没有人说"。
**Flip 条件**:运行时开始报版本号(例如发行物需要被并存的多版本区分)时,这条
改回比对版本。

## 4. WT-09(D-07):维持不做,并复核前提

前提是"没有任何动词会选择一个 worktree"。复核:公开动词表里没有任何一个接受
worktree 或分支,`--root` 是工作区路径而非 worktree 选择器。前提仍然成立,
维持不做,flip 条件不变。
