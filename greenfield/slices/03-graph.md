## 1. 本切片真正的内容不是边,是"一个 store 装多个循环"

GE-01 要求「上游必须在**同一 store**」。而当前实现里,`openLoop` 见到第二次开单
就 `ALREADY_OPEN` —— 一个 store 一个循环。**边无处可指。**

所以切片 3 的地基工作是把 store 从"一个循环的账本"变成"一张图的账本"。这不是
为了图才顺带做的重构;它同时解锁两条早就写在语料里、却一直无法表达的场景:

- **CC-02**:两个循环的 claims 重叠必须被拒——单循环时无从谈起。
- **CC-07「图的地基」**:不相交的两个循环全程交错活动,零互相作废。

## 2. 一处必须先还的债:revision 现在是全局的

设计稿·一致性模型:

> **修订版本是实体级的,不是全局的**:judgment、observation、边校验都只绑自己
> 实体的 revision 与相关 digest。邻居节点的任何活动不影响你——**这是图能并发的
> 前提**,是公理 5 的直接推论。

当前 `projection.mjs` 写的是 `next.revision = record.seq`,**全局的**。一个 store
一个循环时这没有差别;多循环之后它立刻变成设计明确要避免的那个失效模式——
**邻居写一条记录,我这一轮的乐观并发检查就失败**,正是旧实现里"认证被不相交邻居
打碎"的复现。

裁决:**revision 是该循环自己最后一条记录的 seq**。

内核记录(尾部修复、genesis)不属于任何循环,因而不推动任何循环的 revision——
它们是关于日志的事实,不是关于循环的。**例外**:尾部修复若真的截掉了某个循环的
记录,该循环的 revision 会**变小**。这是对的:调用方持有的 expected_revision 不再
匹配,写入被拒,而"我看到的状态已经不存在了"正是应当被拒的情形。

## 3. 循环身份

**`loop_id` = 该循环 `loop_opened` 记录自身的链上 digest。**

- 内容寻址,公理 5 的直接用法;
- 由构造唯一,不需要计数器、不需要随机数、不需要防重表;
- 边要 pin 的东西本来就是 digest,身份与引用同一种材料。

`loop_opened` 不携带 `loop_id` 字段(它无法记住自己的 digest);**其余每条循环记录
都携带**。内核不认识 `loop_id`——它是日志内核,不是循环内核;分流发生在投影层。

展示时截断为前 12 位,与 store id 同一手法;**判等永远用全串**。

## 4. 边

```
depends_on { loop_id, pinned_certification_digest | null }
```

- **开单时声明**(`open --depends-on <loop_id>[@<digest>]`,可重复);
- **开单时校验**:上游在同一 store、非自身、非 abandoned;
- **零追加**:任何被拒的 open 都不产生记录(与 CC-02 同一条);
- **一经开启不可 amend**。理由:边是这个循环"是什么"的一部分,不是它的参数。
  改变依赖关系等于换一个节点,而换节点应当是开一个新的。

### 4.1 没有查环器〔实现期修订〕

规格初稿按 GE-01 的字面写了"开单时查环"。实现时发现**环根本无法构造**:

1. 边只能指向**已经存在**的循环(`EDGE_UNKNOWN_UPSTREAM`);
2. 已存在的循环**永远无法获得**新的边(§4:边不可 amend)。

于是追加顺序就是拓扑序,A→B→A 没有出生的途径。**写一个永远不会命中的查环器,
正是审计花时间删掉的那类东西**;它还会让读代码的人以为这里存在一个需要防的风险。

改为:实现里没有查环器,测试断言的是**保证它的那条性质**(amend 加不上边),
并把这段论证写在测试里。若将来边变得可变,这条论证失效,查环器必须同时回来。

v1 只有这一种边。监督边、仲裁边、调度边显式列为非目标(设计稿),各自带准入条件。

## 5. 依赖门:拦认证,不拦工作

GE-02 的两句话必须同时成立:

> B 的 satisfied judgment 被拒,错误可判别为依赖未满足;**B 的 observation 照常落账**。

这与收据漂移那条(02-git-receipt §6.2)是同一个裁决:**判据已经跑完了,丢掉这次
观测等于丢掉一次真实的、付过代价的事实**。所以观测照记,认证不给。

依赖满足的判定,三条全中才算:

| 条件 | 出处 |
| --- | --- |
| 上游 terminal 且 outcome achieved | GE-02 |
| 边若 pin 了 digest,逐字匹配上游的认证 digest | GE-03 |
| git 体制下,上游认证 commit 是本循环 HEAD 的祖先 | GE-04(复用 GR-06 机制) |

前两条是纯粹的日志事实,投影可判;第三条要问 git。与收据同构:**`observe` 在观测
时把结果算出来记进轮次**,策略因此仍然是纯函数。观测记录新增
`dependency_state: none | satisfied | unmet`。

未满足时的决策:新决策 **`blocked`**,原因 token `dependency_unmet`〔本切片定版〕。

为什么不用现成的 `suspend`:挂起要人来 `resume`,而依赖满足是**别处自然会发生的
事**,上游 achieved 之后 B 应当自己变回可推进。**需要人干预和只是还没轮到,是两件
不同的事**,合并它们会让"卡住的循环"这个信号失去意义。

## 6. `ready`

只读前沿投影:列出**活动的、且依赖全部满足的**循环。

- **零字节变化**(引用 LK-11):调用前后账本逐字节相同,快照也不写。
- A achieved 之前 B 不在 ready,之后在。
- **运行时不存在任何主动派发路径**(GE-05 末句)。`ready` 回答"哪些可以推进",
  不回答"接下来推进哪个",更不自己去推进。调度器是显式非目标。

## 7. claims 跨循环不重叠(CC-02)

单循环时 `assertClaims` 只查一个循环自己的 claims 互不包含。多循环之后,**同一
store 内任意两个活动循环的 claims 也不得重叠**,否则:

- 两个循环的 receipt 会互相把对方的路径算成"外来内容";
- 更糟,两个循环会各自为同一批文件出具互相矛盾的证据。

拒绝时**零日志增长**(CC-02 原文)。终结与放弃的循环不参与判定——它们的 claims
已经释放。

## 8. 分层与影响面

```
projection.mjs   reduceLoop → reduceStore:records → { loops: Map<loop_id, LoopState> }
policy.mjs       decide(state, { upstreams }):依赖是入参,不是查询
loop.mjs         每个动词接受 loopId;open 返回新的 loop_id
graph.mjs〔新〕  边校验、查环、依赖判定、ready 投影
```

内核(`src/store.mjs` 等)**一行不改**。这是对切片 1 那条边界的检验:如果图必须
动内核,说明当初的分层是错的。

## 9. 不做

- **调度**:`ready` 之后由谁推进,是宿主的事(宿主契约)。
- **监督边 / 仲裁边**:设计稿显式非目标,各带准入条件。
- **跨 store 的边**:GE-01 就写死了同一 store。跨 store 需要一套引用与信任模型,
  不属于 v1。
- **边的删除或改写**:见 §4,换依赖等于换节点。
