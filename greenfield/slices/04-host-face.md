## 1. 这一层不新增语义

前三个切片把语义做完了。切片 4 只做三件事:**让人能用它**(CLI)、
**让人能看它**(查询面)、**让人能带走它**(export)。

判据是明确的:**服务层已经能做的,CLI 一行语义都不许加**(设计稿:CLI 是薄壳,

## 2. store 的种类记在 manifest 里

新增 `store_kind: "git" | "fs"`,创建时定,此后校验。

| 种类 | 位置 |
| --- | --- |
| `git` | `<git-common-dir>/workloop/` —— 多 worktree 共享,删 worktree 不丢历史 |
| `fs` | `<root>/.workloop/` |

### 2.1 种类冲突(FS-07)

一个 fs 根后来被 `git init`,世界就同时提供了两个不同的 store 位置。**这不是可以
自动选择的歧义**——选任何一个都会让另一个位置的读者看到不同的历史。

裁决:**一切动词拒绝并诊断种类冲突**,与"复制体身份碰撞"同一类处理(公理 3
失败即关闭)。恢复手段是人来决定:导出后重建,或移走 `.git`。

同理,git store 上的 `receipt` 在 fs store 上以可判别的错误拒绝——那不是"这个
store 暂时没配好",是**这个 store 不具备那种证据**。

## 3. 寻址:显式优先,发现兜底

设计稿·寻址模型:

> **显式优先**:命令接受 store 路径与 loop id。
> **便利发现**:未显式给出时,从 cwd 向上走目录树找 store 目录——与 git 自己
> 发现 `.git` 同构,零额外机制。

- `--store <path>` 永远优先;
- 否则从 cwd 向上找 `.workloop/`,以及 git 仓库的 `<common-dir>/workloop/`;
- **git store 的 root 是工作树顶层,不是搜索起点**〔评审后修订〕。`--git-common-dir`
  在任何深度都给同一个答案,所以它单独用不能当"向上找":搜索会在第一个尝试的目录
  就成功,把那个子目录当成工作区。root 取 `--show-toplevel`;
- **两者同时存在 = 种类冲突**(§2.1),不猜;
- **显式 `--store` 时,root 由 store 自身推出**〔评审后修订〕,不取调用方站的位置:
  fs store 取 `.workloop` 的父目录,git store 取工作树顶层。拿 cwd 当 root,既会
  报不存在的冲突,也会漏掉真实的冲突——而种类检查正是 FS-07 存在的理由;
- 都找不到 → 拒绝并指路(`init` 或 `--store`),**绝不自作主张创建**(FS-01)。

## 4. 嵌套根双向拒绝(FS-04)

两个 store 嵌套意味着**同一条路径属于两本账**,claims 无从判定归属。两个方向都要拒:

- **向上**:创建位置的任一祖先目录已持有 store → 拒绝(`STORE_NESTED_INSIDE`)。
  走目录树,便宜。
- **向下**:创建位置之下已存在 store → 拒绝(`STORE_CONTAINS_NESTED`)。这需要
  往下扫,**只在创建时做一次**(创建是稀有操作,每次 open 都扫是不划算的)。

向下扫有界:深度上限、条目上限,跳过 `.git` 与点目录。**扫到上限而没扫完时明说**
(诊断里带上"未扫完"),不假装扫干净了——语料 README 立的规矩是不做静默截断。

### 4.1 FS-02:运行时自己的文件不是制品〔评审后补〕

规格初稿把 FS-02 列进完成判据却没有实现它。缺口不是文档性的:`artifactCheckpoint`
会走进 `.workloop/`,于是**账本每追加一条记录,制品 checkpoint 就变一次**。

后果是隐蔽的:`.` claim 的循环每轮 progress signature 都不同,`repeatedFailures`
永远累积不到阈值——**stuck 检测还在那里,但再也不会触发**。一个反复以同样方式失败
的循环会一直跑下去。

裁决:控制面路径(`.git` 与账本目录)从 checkpoint 中排除,与 receipt 用同一份
定义(GR-05 此前只排除了 receipt 一侧,这是两侧)。

## 5. 移动、删除、重建(FS-03)

物理锚取的是 store 目录自身的 dev/ino/birthtime(已实现),因此:

- **改名或移动根** → `.workloop/` 随之移动,inode 不变,**身份不变**;
- **删除根** → store 随之消失。**这是 M3 显式接受的取舍,不是缺陷**;
- **同路径重建** → 新目录、新 inode、新随机 store id,与消失的旧 store 零关联。

留档手段是**事前** `export`。这条必须在文档里写明白,因为它是一个人只会在事后
才想起来的性质。

## 6. 查询面:`status` · `log`(`ready` 已有)

三者都是只读,**零字节变化**(引用 LK-11):不写快照、不修尾部、不取锁。

- `status <loop_id>` —— 目标、claims、生命周期、轮次、在场收据、依赖、下一步指令。
- `log [--loop <id>]` —— 记录流,可按循环过滤。**默认输出的是记录,不是解读**;
  一个人要能拿它和磁盘上的字节对照。
- `ready` —— 前沿(切片 3 已实现)。

`status` 与 `next` 的关系:`status` 里嵌的指令**就是 `next` 的返回**,同一个函数,
不是另一份实现。两份会漂。

## 7. `export`

把一个 store 变成一份**自足、可独立验证**的文件:manifest、全部记录、头 digest。

- 只读;导出不改 store 一个字节。
- 导出物可被独立校验:链、digest、CRC 都在里面,验证不需要原 store。
- **不做 import**。恢复一个消失的 store 意味着伪造它的物理锚,而锚的意义正是
  "这份身份属于这个位置"。导出物是**留档与审计**,不是备份还原。

## 8. CLI

```
workloop <verb> [--store <path>] [--loop <id>] [options]
```

- 薄壳:参数解析 + 调服务 + 打印 JSON。**零业务判断**——包括**不发明默认值**
  〔评审后修订〕。初版给了 `--budget` 默认 10、`--mode` 默认 commit,而服务层两者
  都没有默认:**那是"一个循环能跑多久"的政策,被放在了没人会去看的地方**。
  服务层同时补上了缺失的 `BUDGET_REQUIRED` 校验——CLI 的默认值一直在替它遮丑。
- **认不出的 flag 拒绝,不丢弃**〔评审后修订〕。`--bugdet 5` 原本能干净地解析并
  消失,循环拿到的是那个不存在的默认值。
- 成功 exit 0;拒绝 exit 非 0,stderr 打印 `code: message`,**code 与服务层的
  错误码逐字一致**——人在 stderr 里 grep 到的,就是测试里断言的那个。
- 输出是 JSON(可被脚本消费),不是给人读的表格。给人读的那层不属于本切片。

## 9. 打包闭包(HF-08)与工作流文本(HF-09)

- **HF-08**:发行物只含现行运行时——不含退役模块;skill 文本只引用公开动词表里
  真实存在的动词;**文档里写的判据契约与实现一致**。这三条都用测试压住:动词表
  从 `loop.mjs` 的导出取,不是手抄一份。
- **HF-09**:随发行的工作流文本,每一步都有**可判定的完成条件**。

## 10. 不做

- **`import`**:见 §7。
- **fs receipt 适配器**:设计稿的领域模型提到"非 git: 文件 digest 集",但 FS 族
  保留场景没有一条需要它(FS-08 证据通道随 M1 出局)。**没有场景要的东西不做**。
  **Flip 条件**:出现一个需要 fs 循环出具制品证据的场景。
- **安装器(HF-06)**:M1 之后它只剩"幂等地安装 skill 资产、版本化激活、不碰宿主
  配置"。这需要一套发行形态,而绿地还没定义发行形态。挂进 DEBT。
- **给人读的输出层**:JSON 够脚本用;表格、颜色、分页不属于最小可用。
