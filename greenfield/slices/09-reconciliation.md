# 切片 9:账本否认的提交

日期:2026-07-25
状态:规格先行,写定于实现之前。

上承:[DEBT](../DEBT.md) D-01、[02-git-receipt §8.2](02-git-receipt.md)。
完成判据:一个账本没有记录的 workloop 提交**可被发现且被指名**,前八个切片不回归。

## 1. 缺口比挂账时写的小

挂账时写的出路是"启动时对账,差额记为恢复记录,需要新动词与新场景"。重新看,
**大半已经被别的东西补上了**:

切片 2 评审时加了"为已有提交作证"那条路径(`git commit --only` 无可提交时,为
已经持有任务路径的那个提交作证)。于是**同一个 command id 的重试会自愈**:崩溃
发生在提交之后、追加之前,重试时 git 说无可提交,运行时转而为那个提交作证并落账。

真正剩下的只有一种:**崩溃之后没有人重试那个 command id**。那个提交就永远躺在
仓库里,而账本不知道它。

## 2. 所以本切片只做一件事:让它无法不被看见

不新增动词,不新增记录种类。**运行时对"我造过但没记下的提交"必须有能力指名**,
而不是只能承认"理论上可能存在这种东西"。

**能被发现,和被自动修复,是两件不同的事,而前者才是这个运行时的本分。**修复要
动 git 历史(revert、amend、reset),那是执行,归宿主(宿主契约)。

## 3. 机制:提交自己带着它属于谁

workloop 造的提交带 trailer:

```
workloop receipt

Workloop-Loop: sha256:…
Workloop-Command: <command id>
```

于是对账是精确的,不靠猜提交信息:

- 从 HEAD 往回走,收集带 `Workloop-Loop: <本循环>` 的提交;
- 其 `Workloop-Command` 在账本里找不到对应 `loop_receipt` 记录的,就是**账本
  否认的提交**。

trailer 而不是提交信息正文:trailer 是 git 自己认识的结构(`git log
--format=%(trailers)`),而一行自由文本任何人都能写成一样。

### 3.1 走多远,以及走不完时怎么说

从 HEAD 往回,走到**最后一条已记录的收据提交**为止;没有已记录的收据时,以
提交数为界。**撞到上限而没走完时明说**——语料 README 立的规矩是不做静默截断,
而"我没找到"和"我没找完"是两回事。

## 4. 在哪里说

`status` 里一个字段:`unrecorded_commits`。只读,零字节变化。

不放进 `next` 的决策:**它不是循环的下一步**。一个账本否认的提交是关于仓库的
事实,由人处置;把它做成 `decision` 会让循环停在一个它自己解决不了的事情上。

## 5. 自愈的那条路仍然在

发现之后,人可以用**同一个 command id** 重跑 `receipt`——那条路径会为已有提交
作证并落账,缺口就补上了。文档要写明这一点,因为它是"发现"之后最自然的下一步。

## 6. 不做

- **自动修复**:见 §2。
- **新的恢复动词**:没有它要做的事——自愈走的是现成的 `receipt`。
- **跨循环对账**:一个提交带的是它属于哪个循环;`status` 是按循环问的。
