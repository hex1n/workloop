## 2. 嵌套:两条规则的正面冲突,以及它们各自对在哪里

切片 4 §4 立的规矩:**嵌套 store 双向拒绝**,理由是"同一条路径属于两本账"。
WT-02 说的是:**嵌套子仓有自己的 store**,向上发现在第一个 store 处停止。

已实测:当前实现拒绝了一个嵌套 git 子仓建立自己的 store(`STORE_NESTED_INSIDE`)。

两条规则各自的理由都成立,冲突源于我把"嵌套"当成了一个纯路径概念。**它不是。**

- FS-04 真正要防的是**两本账claim 同一批文件**;
- 而一个嵌套的 **git 子仓,它的文件根本不是父仓的文件**——git 自己就是这么算的:
  父仓不跟踪子仓的内容,父仓的 pathspec 匹配不到它们。

裁决:**嵌套在两个 store 的工作树确实不同时,是允许的**。可判据:两者都是
git 种类,且**各自的 git common dir 不同**。其余一律照旧拒绝。

这条判据不是约定,它落在一个真实性质上:**git 自己划的树边界**。fs store 没有
这样的边界(它的 checkpoint 会走遍根下的一切),所以 fs 一侧不放宽。

**Flip 条件**:若将来 fs store 获得可判定的子树边界(例如显式的排除清单),
这条可以按同一理由放宽。

### 2.1 豁免必须两个方向都真的能生效〔评审后修订〕

初版把这条裁决写对了,实现却在两处漏掉:

1. **向下扫描看不见 git store**。它在能看到 `.git/workloop` 之前就跳过了 `.git`,
   于是"根下已有 git 账本"这件事**从来无法被发现**——豁免那段过滤是死代码,而它
   掩盖的是一个真洞:fs store 可以建在含有嵌套 git 账本的根上,而它的 checkpoint
   会走进去。现在直接查 `<dir>/.git/workloop`,而不是往里走。
2. **扫到的 store 种类被猜而不是被读**。过滤器对每个位置都硬写 `kind: git`,于是
   一个 `<dir>/.workloop` 的 **fs** 账本被当成 git 的,新建的 git store 被放行——
   **这是本次提交引入的回归**,而它正是这条检查存在的唯一理由。现在读 manifest。
3. **向上走到第一个 store 就停**。被豁免的近邻不该终止搜索:更上层的 fs 账本会
   穿透那条仓库边界。改为继续走。

第 3 条修好之后有一个副产物:fs 账本与嵌套仓账本**两个顺序都被拒**,于是"上层 fs
+ 中层独立仓"这种三层布局根本无法构造——不是没被发现,是造不出来。

## 3. 发现在第一个 store 处停止(WT-02 后半)

`discover` 自下而上走,**在遇到的第一个 store 处返回**,不穿透到父仓。当前实现
已经是这样;本切片补测——一条没有测试压着的性质,和一条没有的性质在下一次重构
面前是一样的。

## 4. 移除工作树:旧真相不因此改变(WT-05)

`git worktree remove` 之后:

- 该 worktree 里开出的循环**历史完整保留**——store 在 common dir,worktree 只是
  一个观察位置;
- 同路径重建一个 worktree**不复用任何身份**:store 身份来自 common dir,循环身份
  来自开单记录的 digest,两者都与 worktree 的路径无关;
- 已消失的工作树上的循环仍可查询;需要工作区的动词(`observe`、`receipt`)以
  可判别的错误拒绝——**那不是"暂时不可用",是那个位置不存在了**。

## 5. export 的落盘约束(WT-13)

场景原文:"maintenance 锁下的字节精确出版,禁止落在活体根内"。

- **字节精确**:导出物含全部记录与头 digest,链可脱离原 store 独立校验(已实现并
  已测)。
- **禁止落在活体根内**〔本切片定版〕:运行时**不写文件**——`export` 返回数据,由
  宿主决定往哪放(宿主契约:运行时不拥有执行)。所以这条不变式的运行时侧是:
  **`export` 不产生任何写入**,包括不写快照、不修尾部。已测(切片 4"只读动词零
  字节变化")。落在哪里是宿主的决定,运行时无权也无从干预。
- **maintenance 锁**:旧世界的锁类随 M6 收缩。`export` 是纯读,取锁只会让它可能
  失败,而一个只读操作没有理由因为别人正在写就拒绝回答。**不取锁**,并接受
  "导出物可能是某一瞬间的尾部"——这正是它记录 `head_digest` 的原因。

## 6. WT-09 不做

"选择既有 worktree 必须显式验证 branch 与 base。"

**没有任何动词会选择一个 worktree。** 运行时不创建工作树、不切分支(M4:那是执行),
宿主把工作区交给它。于是这条校验没有调用者——**没有写入者的机制正是审计花时间清掉
的那一类**。

**Flip 条件**:出现一个接受 worktree 作为参数的动词。届时这条校验必须同时到位。
挂进 DEBT。
