# 第一性推导审计(2026-07-25)

对象:`greenfield/scenarios/` 86 条场景(提交 `41c97c6`)。
起因:语料由旧门禁逐案翻译而来,继承了旧实现对"这个领域由哪些实体构成"的
全部回答。删除旧代码防不住这种继承,只能逐条推导。

## 三问

1. **世界性**:它保护的失败模式,在**根本没有 workloop 这个东西**的世界里
   也存在吗?(即成因是 Git / 文件系统 / 进程 / 并发 / 宿主的性质)
2. **机制衍生**:还是它在保护某个**自选机制**的正确性?
3. **消失测试**:如果绿地不引入那个机制,这条是否直接消失?

裁决顺序是**先裁机制、再定场景**——场景的去留是机制裁决的推论,不能逐条独立判。

## 一、机制裁决

### M1 证据通道(hook)——**删,降为 flip 条件下的可选适配器**

推导:设计稿公理 2 规定只有运行时亲自观测的事实进入判断,并明确 hook 证据
"永不做控制"。那么它对循环判断的贡献为零,唯一用途是"谁在何时写了什么"的
审计线索。而 receipt 已经权威回答了"制品变成了什么样"——判断需要的是后者。

它的成本却是全库最高的:它是 **M2 目标优先路由**存在的唯一理由(宿主递来的
是一个文件路径,运行时必须回答"这属于谁"),并由此拖出 locator、会话唯一性、
控制路径排除、多目标 patch 解析、profile/mode 矩阵、安装期 hook 协商。

**Steelman(如实记)**:它能更早发现"agent 写到了 claims 之外"。
**反驳**:receipt 时刻同样会发现(任务范围 stage + 外来变更 → receipt 判
uncertain,见 GR-01/03/04),运行时本来也无力阻止(它不是 sandbox)。所以它
买到的是**提前量**,不是新能力,代价是约 10 条场景加整套路由本体论。

**Flip 条件**:若将来判定 claims 边界需要**实时拦截**(即 deny 真的要拒绝
写入),该机制必须回来——但那同时要求修订"宿主拥有执行审批"的公理。

### M2 目标优先路由——**删,改显式寻址 + 向上发现**

推导:随 M1 消失。CLI 调用者完全可以显式说明 store 与 loop;人体工程学由
"从 cwd 向上走目录树找 `.workloop/`"解决——与 git 自己发现 `.git` 同构,
零额外机制。

区分要点:**"从路径发现 store"是廉价的;"locator 文件 + claim token + 两阶段
认领 + 伪造检测"不是**。后者的存在理由是 M3。

### M3 store 数据托管在受管 home + 根内放 locator——**删,store 住在它描述的根内**

推导:store 数据不在它所描述的位置,才需要一个正向指针,指针才需要防伪、
两阶段认领、孤儿检测、过期检测。绿地直接问:**store 能不能就放在根里?**
能——git 放 common dir 内,非 git 根放 `<root>/.workloop/`。

**代价(显式接受)**:根被删除时其循环历史随之消失,不再"留档可审计"。
留档手段改为显式 `export`(WT-13)。git 场景不受影响:store 在 common dir,
删 worktree 不丢历史。

**碰撞检测不随之消失**:`cp -r` 与 clone 让两个位置声称同一 store 身份,
这是文件系统与 git 的性质,**必须**检测。手段简化为:genesis 记录物理锚
(dev/ino/birthtime 或 git common dir 身份),读取时比对。

### M4 placement / exclusive worktree 创建——**删**

推导:创建 worktree 与分支是对仓库的**修改**,即执行——与公理"运行时永不
拥有执行"正面冲突。宿主与 agent 本来就会 `git worktree add`,且更灵活。

它引入的 pending intent 状态机、恢复困境、以及本语料上一版新增的"放弃出口",
全部是自造问题的自造解法。**给一个本不该存在的机制补逃生口,是继承污染最
典型的形态。**

**保留其中的真不变式**:节点绑定到一个已存在的隔离现场时,**校验**(只读)
其 branch/base 符合预期(WT-09)。校验不是执行。

### M5 attachment 恢复族(epoch / claim token / reattach / fork-identity)——**删**

推导:整族是 M3 的衍生。locator 不存在,就没有"复制体转正""身份分叉"的问题。

**保留 attachment 本身,但改名 Site(现场)**:一个 git store 对应多个 worktree
现场,"哪个现场"是 git 的性质,不是选择。故 WT-03/04/05 的共享、移动、移除
语义保留。改名理由:`attachment` 这个词的动机来自"locator 把 store 附着到根",
locator 出局后该动机不复存在;`Site` 是它现在实际的意思。语料沿用旧词处按
README 词汇映射读作 Site。

### M6 全局 outcome 投影 / 跨 store 分片——**删**

推导:用途是跨 store 聚合查询("我所有仓库的任务")。无需求证据。绿地逐
store 查询;确有需要时做纯客户端聚合,不进内核。
**保留**"投影是可弃缓存、损坏不毒化"这一公理级性质(LK-12 主体)。

### M7 会话唯一性(一会话一活动节点)——**删,与图目标冲突**

推导:它存在是因为 hook payload 只有 session_id、没有 loop id,必须靠"一会话
一节点"才能无歧义归属证据。随 M1 消失。

**而且它与图直接冲突**:图工程的常态就是一个 agent 推进 DAG 的多个节点。
保留会话唯一性等于禁止图。

**保留**:会话身份仍记录,用于 provenance 与参与者记账(join 语义,CC-05)。

### M8 不兼容状态归档——**删**

纯迁移遗物。绿地零存量。

### M9 claims 冲突检测——**保留(世界性)**

推导:两个 agent 改同一文件互相覆盖,是并发的性质。运行时无力阻止写入,
但 claims 让两个节点的**意图**不重叠,从而 **receipt 能界定"我的路径"**
(GR-01 依赖它)。这是 receipt 得以存在的必要输入,不是可选装饰。

### M10 锁分类全序——**保留,分类集重定**

死锁避免是并发的性质。但删掉 M6(outcome 锁)与 M4 之后,分类集可能缩到
2–3 类,LK-01 的复杂度大降。

### M11 事务相位——**保留,相位数收缩**

"部分状态如实上报"是世界性(崩溃随时可能发生)。但相位数随投影数,删掉
locator 与 outcome 发布后可能只剩 append + snapshot。

### M12 分段 / 快照 / 崩溃恢复——**保留(世界性)**

日志无限增长、写入可能中断,都是必然。

## 三、设计稿待改点

`docs/plans/2026-07-25-greenfield-redesign.md` 需要以下修订(未执行,待确认):

1. **删除证据通道**:「宿主契约」一节中 hook 作为可选证据通道的表述改为
   非目标 + flip 条件;动词表删除相关面。
2. **删除 placement 概念**:节点绑定现场改为只读校验。
3. **存储层改写**:store 住在根内;删 locator;碰撞检测改为物理锚比对;
   显式记录"根删除即历史消失,export 为留档手段"的取舍。
4. **寻址模型改写**:目标优先路由 → 显式 store/loop + 从 cwd 向上发现。
5. **删除会话唯一性**:会话身份降为 provenance,并说明这是图的前提。
6. **动词表收敛**:此前为语料补入的 `join`、`receipt`、recovery 族中,
   reattach / fork-identity / archive 随机制出局;recovery 族只剩
   torn-tail 与 append 失败续行。
7. **交付切片重估**:切片 4「宿主面」的主体(hook 适配器)出局,规模显著
   缩小;切片 1 的锁与相位复杂度同步下降。

## 四、审计的边界

- 本审计只裁"是否属于绿地内核",不裁"旧实现当年该不该这么做"——旧世界的
  这些机制在它自己的定位(stop gate + 证据记账)下多数是自洽的。
- **M1 是本审计影响最大的一条**,也是最可能被推翻的一条:它假定循环判断
  不需要实时写入拦截。若该假定不成立,M2/M7 及其衍生场景需要整体回流。
- 出局 ≠ 删除文件:场景原文保留在语料中并标注驱动机制,便于 flip 条件触发
  时整族恢复。
